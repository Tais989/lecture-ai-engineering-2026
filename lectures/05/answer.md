## 演習

### 比較に使った質問
「第2回の説明では、LoRAは何を固定し何を学習しますか？ QLoRAは何を加えますか？」
（モデル: gemini-3.5-flash-lite、対象資料: 第1〜3回の本講義、根拠: 第2回 p.52）

### 4経路の比較

| 経路 | 正答／引用根拠 | 時間(秒) | 入力／出力 tokens | 生成API推定 USD |
|---|---|---|---|---|
| 全文投入 | 一部正答／第2回 p.51, 52 | 1.65 | 117,025／151 | $0.004529 |
| ベクトル検索 | 正答／第2回 p.51, 52 | 24.03 | 3,028／191 | $0.001386 |
| Tree | 正答／第2回 p.52 | 5.89 | 9,214／376 | $0.003704 |
| Graph | 正答／第2回 p.51, 52 | 3.15 | 5,771／201 | $0.001686 |

### 気づき
- 全文投入は入力が約117千トークンと最大だったが、QLoRAの説明は「圧縮する処理を組み合わせる」と曖昧で、「4bitに圧縮」まで書けなかった（一部正答）。資料に入っていても、必ず使われるとは限らない例だと思う。
- 入力量はベクトル検索（3,028）が最小で、Graph（5,771）、Tree（9,214）、全文投入（117,025）の順だった。
- Treeは章の候補一覧を順にたどるため、`browse_tree` を4回呼び（講義一覧→第2回→該当章→p.52）、モデル応答は5回になった。
- 時間は1回の計測で、API側の混雑でばらつく（後の再実行では30秒以上かかり、503エラーも出た）。時間から方式の優劣は決められない。
- この質問は p.52 だけで根拠がそろうため、どの方式でも答えられた。複数ページにまたがる質問での差は今回は未確認。

### やったこと
`app/config.py` の `RAG_TOP_K`（ベクトル検索で返すページ数）を、5から1に変更した（21行目、1か所のみ）。同じ質問を `--trace` 付きで実行し、変更前後を比べた。比較後は元の値（5）に戻した（`git diff --stat` で差分なしを確認）。

### 結果

| | 変更前（TOP_K=5） | 変更後（TOP_K=1、3回） |
|---|---|---|
| ツールの呼ばれ方 | `search_materials` 1回 | 同じ（1回） |
| 引用ページ | p.51, p.52 | p.52のみ |
| 答え | 正答 | 正答（LoRAの固定と差分学習、QLoRAの4bit圧縮がそろう） |
| 入力 tokens | 3,028 | 1,191／1,191／1,189 |
| 時間 | 24.03秒 | 42.64秒／33.80秒／59.24秒 |
| 推定USD | $0.001386 | $0.000955／未記録／$0.000817 |

### 気づき・疑問
- 検索件数を5から1にすると、入力トークンは約6割減り、費用も下がった。この質問は p.52 だけで答えられるため、答えの質は変わらなかった。
- 一方、p.51（PEFT）の補足は引用から消えた。根拠が複数ページにまたがる質問では、1件だと足りなくなる可能性がある。
- 検索語は毎回少しずつ違った（「加える」が付く回と付かない回）が、返ったページは同じ p.52 だった。
- 時間は33〜59秒とばらつき、変更前（24秒）より長かった。入力トークンはほぼ同じなので、検索件数ではなくAPI側の混雑が主因と考える。1〜3回の計測では時間の優劣は判断できない。
- 疑問：複数ページが必要な質問（例：コンパクションとセッションをまたぐメモリの違い、第3回 p.13, 39, 40）で `RAG_TOP_K=1` にすると、根拠が足りなくなるか。今回は試していない。
